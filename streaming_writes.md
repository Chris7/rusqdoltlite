# Bounded blockcache VFS and streaming writes

## Goal and contract

Make `cachefile.bcv` a bounded pool of reusable on-disk block slots. A block
evicted from that pool must leave no separately allocated local payload behind.
Under cache pressure, the VFS may PUT immutable block objects to the bucket,
but those objects remain unpublished. Only the existing explicit
`BlockCacheVfs::upload(alias)` operation may publish a new container manifest.
An update larger than the cache must complete by staging and reusing slots.
DoltLite and the remote server must not acquire VFS-specific commit hooks.

The VFS must maintain these states for each logical database block:

| State | Local payload | Remote source | May reuse its slot? |
| --- | --- | --- | --- |
| Published | Optional cache slot | Published manifest | Yes, when unpinned |
| Dirty | Required cache slot | None for current bytes | No, until staged |
| Staged, unpublished | Optional cache slot | Durable staged-object mapping | Yes, when unpinned |

Never delete a bucket object merely because its local cache slot is evicted.
The staging mapping must identify container, database, logical block position,
generation, and object ID; block ID alone is insufficient. A later write to a
staged block supersedes its staged mapping without changing the published
manifest. A read can recover current bytes from a resident dirty slot, the
staging mapping, or the published manifest, in that order.

## Implementation tasks

- [x] **1. Establish the baseline and test seams.** Record the current cache
  allocator, local metadata schema, read-miss rule, upload sequence, and
  physical `cachefile.bcv` size behavior. Preserve unrelated worktree changes.
  Add deterministic fault points around object PUT, staging-map persistence,
  slot reuse, and manifest PUT. Verify those points can be exercised by tests.
- [x] **2. Specify and enforce a hard cache-file cap.** Give `CacheSize` clear
  block-aligned capacity semantics and reject invalid values. Stop
  `bcvfsAllocCacheEntry()` from adding slots beyond the cap. Maintain a free
  slot or reclaim a clean, unpinned slot; when none is safe, stage dirty blocks
  and apply bounded backpressure rather than growing the file. Handle an
  existing cache file larger than a newly configured cap explicitly, without
  silently discarding dirty data. Verify every slot below the high-water mark
  is either mapped to a resident block or on the reusable free list, including
  after restart. Reuse or overwrite the slot; do not create per-block disk
  files. Invalidate an evicted clean block's persisted slot mapping before
  overwriting its bytes; after a crash, no old block ID may point at a reused
  slot. This is a space bound, not a secure-erase guarantee.
- [x] **3. Make staged-block bookkeeping recoverable.** Extend the local
  manifest/metadata state so a successfully uploaded block remains addressable
  after its cache slot is reused and after process restart. Use one
  authoritative mapping for final manifest composition. Persist the mapping
  *before* freeing the slot; if persistence fails, retain the dirty local
  payload. `blocksdb.bcv` currently opens with `PRAGMA synchronous=OFF`, which
  is insufficient for this ordering guarantee after power loss. Change the
  bounded mode to use a genuinely durable metadata commit (or an equivalent
  durable remote staging journal), and verify the ordering with fault
  injection. A persisted clean-cache mapping must likewise never survive
  when its slot bytes were overwritten or not durably written; invalidate or
  verify it before serving a restarted cache hit. Reconcile the physical
  cache-file length and metadata on open so no orphaned tail of local block
  payload remains unaccounted for.
- [x] **4. Stage blocks during writes without publishing.** On a configurable
  high-water mark, and whenever allocation would hit the cap, select an
  eligible dirty block, snapshot its generation, PUT its complete block bytes,
  verify success, persist its staged mapping, then release its slot. Do network
  I/O outside the VFS mutex. Handle concurrent writes, duplicate staging,
  partial-tail blocks, retries, and rewrites of previously staged blocks. A
  failed or ambiguous PUT must never cause eviction of the sole recoverable
  copy. Track superseded staged objects for safe later garbage collection.
- [x] **5. Update read, copy-on-write, and truncate paths.** Cache misses may
  fetch current staged blocks even when they lie beyond `nBlkOrig`; published
  misses continue to use the published manifest. Preserve read-your-writes
  after staging and eviction. Never evict a pinned or unstaged dirty block.
  Correctly supersede mappings on overwrite and remove mappings on truncate.
  Ensure prefetch, multiple databases, and pinned snapshots obey the same
  state rules.
- [x] **6. Keep `upload()` as the sole publication operation.** Retain the
  existing upload lock/checkpoint protections. Stage any remaining dirty
  blocks, compose one manifest from current published and staged mappings,
  and publish it with the existing conditional ETag check. Only after a
  confirmed manifest PUT may staged blocks transition to published. On block
  failure, CAS conflict, timeout, or ambiguous manifest response, retain
  enough state to retry or reconcile the remote manifest; never mark a block
  published on an unconfirmed response. Do not add manifest publication to
  `xWrite` or `xSync`.
- [x] **7. Carry and document the change cleanly.** Put CBS C changes in a new
  numbered `libdoltlite-sys/patches/blockcachevfs/` patch applied to staged
  sources; leave vendored `cloudsqlite/` and `doltlite/` pristine. Update Rust
  configuration/docs and patch-series docs for the hard cap, staging,
  explicit upload, retry, and durability behavior. Preserve the default VFS
  choice and the pending named-remote-VFS work.

## Tests and manual acceptance

- [x] **8. Prove capacity and slot reuse.** With a tiny cache, write much more
  than its capacity in one logical update. Inspect `cachefile.bcv` throughout
  the write and after restart: its length never exceeds the configured cap,
  slot positions are reused, and no evicted block has a separate local payload.
  Exercise a full scan and repeated scan under the same cap. Verify exhaustion
  with all slots pinned or failed uploads returns a controlled error or waits,
  not an allocation beyond the cap.
- [x] **9. Prove pre-publication isolation and reads.** Before `upload()`, check
  the bucket manifest bytes/ETag using an independent client: they are
  unchanged even though staged objects exist. Read staged, evicted, newly
  appended, rewritten, and truncated blocks through the writing VFS. After
  `upload()`, detach/reattach with a fresh cache and verify exactly the final
  contents. Include a DoltLite native remote push larger than the cache.
- [x] **10. Prove crash and `synchronous=OFF` caveats.** Inject termination or
  errors after block PUT, after staging-map commit, after slot reuse, and after
  manifest PUT but before local cleanup. Restart and verify that every current
  block is recoverable locally, from a staged object, or from the published
  manifest. Use a fault-injected storage layer that discards *unsynced*
  metadata writes to model power loss; `SIGKILL` alone does not do so. Show
  that a slot is never reused when its staged mapping would be lost by that
  model. Assert the chosen metadata durability mode/behavior so accidentally
  restoring `PRAGMA synchronous=OFF` fails the regression test.
- [x] **11. Prove failure and compatibility behavior.** Inject failed PUTs,
  interrupted uploads, manifest CAS conflicts, ambiguous responses, and
  concurrent readers/writers; verify no missing references or premature
  deletion. Run Google JSON and S3 emulator integration tests, upstream CBS
  tests for both backends, workspace tests with `blockcachevfs` and
  `blockcachevfs remote`, formatting, Clippy, and `git diff --check`.
